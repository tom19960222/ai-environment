# 技術研究與實驗報告寫作

把已有資料整理成一份沒參與研究的人也能理解、查證和據以判斷的報告。保留 `writing-experiment-reports` 名稱以延續既有使用方式；寫作要求同樣適用沒有實測的研究。

正文預設使用台灣繁體中文，像熟悉技術的同事在說明事情。使用者指定的語言、格式、讀者、範圍與交付位置優先。本 skill 可獨立使用，不依賴特定 repository、網站格式、其他 skill 或 agent 名稱。

## 先沿用已定事項，再辨識證據

先讀本題的原始問題、讀者與用途、已有草稿、相關證據和已接受的決策。確認這次是新文章、改寫既有文章，還是階段性成果；沿用指定的交付格式。需要補齊的事實先自行查閱，只問會改變研究範圍、結論或成品的未決問題。不要因啟用本 skill 而重開一次 grill、逐節批准或重問已確認的大綱。

按實際材料選擇寫法；同一份報告可以混合不同證據，但每項主張的依據必須清楚。

| 手上的證據 | 報告要交代什麼 | 能支持的結論邊界 |
|---|---|---|
| 實驗與量測 | 環境、改變項、方法、已有事前預期、實際觀察、比較條件與建議 | 這次環境與負載下觀察到的結果，不能自動擴大成普遍保證 |
| 原始碼或文件 | 問題、目標版本、觸發條件、關鍵處理路徑、來源位置、實作限制與推論 | 實作如何處理或文件如何描述；不能冒充現場延遲、吞吐量、故障率或穩定性實測 |
| 混合材料 | 各結論由哪種證據支持、彼此吻合或衝突之處 | 實測只覆蓋實際測過的部分；其餘保持文件、原碼或推論的身分 |

只有原始碼／文件的報告，同樣使用下列寫作與審查要求；省去不適用的實驗欄位，不製造虛構的受測環境、事前預期或結果。提出補測方法時明示尚未執行。本 skill 本身不授權執行實驗、修改受研究的系統或發布；沿用當次已提供的授權。

## 先讓讀者理解，再提供追查細節

長報告開頭用約兩到三分鐘可讀完的篇幅交代：要回答什麼、結論或建議、主要證據、適用條件、最重要的限制，以及下一步。短報告按需要縮短，這不是最低篇幅。若未能下定論，開頭就說明目前能確認什麼、哪個缺口會改變決定。

後文順著問題與判斷展開：為什麼研究、必要背景、證據、解釋、建議與限制。正文詳述會改變理解或決策的內容；完整實驗清單、原始資料索引及細節可放附錄或隨報告交付的證據索引。不要讓讀者必須開另一份舊報告，才能理解本篇的前提和主張。

寫作時讀 [report-template.md](report-template.md)，按材料選用段落。它提供安排方式，並非每篇都必須填滿的表單。

- 用連貫段落說清楚情境、做法、發現與意義；表格用於真正需要比較或對照的內容。完整性不等於每個實驗都占一樣長的正文。
- 以事情的名稱代替內部代號，例如「停止一台儲存主機」；不要讓讀者反覆解碼 `R1`、`H-033`。追查必需的 run ID 可放連結、括號或附錄，先說它代表什麼。
- 保留精確的命令、設定、指標、alert rule 與程式介面名稱。其他敘述用自然中文，避免一句話頻繁切換中英文和縮寫。第一次出現讀者不熟的名詞，在使用處簡短說明它的作用。
- 句子直接說明證據與含義，刪除沒有資訊量的套話。縮短文字時，保留會影響判斷的前提與限制。

## 數字與證據的寫法

讀者不應靠倍率心算實際影響。例如先寫「p99 從 18 ms 增加到 88 ms，多了 70 ms」，再視需要提供倍率。正式統計判準若使用比例，保留其定義並另外給直接數值；不能為了改寫文案而更換統計方法或通過標準。

比較前核對版本、量測路徑與層次、負載、時間窗、單位、樣本範圍、分母及統計方法。不同口徑的數字可以並列說明差異，但不能直接相除、排名或互相替代。沒有基準值就明示缺少，不能從不充分的資料補出 ms；零基準或不適合用倍率的結果改用有意義的直接值與差異。定性觀察不必硬算倍率。

重要主張附上真正支持它的來源位置：原始碼的 repository、tag／commit、檔案與符號或行號；文件的版本與章節；量測的環境、run 與資料位置。引用放在相關敘述旁，使用可辨識的名稱，不讓證據代號取代說明。網址存在、模型同意或曾有人寫過，都不等於已查核。

明確區分「實際觀察」「文件／原碼顯示」「依此推論」「建議」與「尚未確認」。條件跟著結論出現；遠處的限制章節無法修正前面無條件的保證。來源互相衝突時先核對版本、設定與方法，保留仍未解釋的差異。

### 有實驗資料時

- 交代受測鏈路、相關硬體與軟體、負載、時長、重複次數，以及確實採用的判準和有效性檢查。未做過的防噪音、交錯測試或生效驗證不能補寫成已執行。
- 若存在實驗計畫，讓每個規劃項目都能找到去向：已執行、併入何處、未執行或略過及原因。另記執行中斷、量測無效或待補證的情形；嘗試執行不等於取得有效結果。不要用分類數字製造假完整。
- 對會影響判斷的實驗，交代改了什麼與值域、為何測、事前預期、實際結果及建議。可用敘事或表格，這些是需要回答的問題，不是五個固定小標題。
- 事前預期只能來自當時留下的紀錄。沒有就寫「未留存事前預期」，把事後解釋分開；預期被推翻的結果不可事後改成符合預期。預設值也需有版本與環境依據。
- 呈現無改善、反效果、弱訊號、資料修正與會改變結論的方法問題。沒有辨識出差異不代表效果相等，也不代表永久無效。

### 只有原始碼或文件時

沿著問題解釋：什麼條件觸發、經過哪些關鍵處理、參數如何影響路徑、在哪些邊界不成立。只展開支援結論所需的程式細節，避免逐函式導覽。將「該版本實作會走的路徑」與「實際環境是否觸發、影響多大」分開；沒有實測仍可得出有邊界的研究結論。

## 建議要對得上證據

建議說清楚做什麼、為什麼、適用條件與依據。調參報告提供有證據支持的值或範圍，以及適用時的變更方式（執行中、重啟、重建等）。證據不足時，可以建議維持現況、先取得基準或補驗特定假設，不必硬給新數值。

推論性建議或候選驗收門檻要標明身分與依據，不能和已驗證建議混在一起。需要補證時，說明要排除哪個不確定性、觀察什麼，以及什麼結果會改變建議；不要擴成無關的實驗計畫。

## 修訂要重新整合全文

使用者或 reviewer 指出問題後，把修正放回適合的位置，替換過時說法、合併重複段落，重新檢查摘要、論證、表格、建議與限制是否一致。若主線改變，就重排結構；避免每次修訂都在文末追加一塊說明。

內容錯誤若也出現在本次交付的其他成品，連帶更正。對當次範圍外的文章或網站，指出受影響位置，不擅自擴張修改或發布。交付前完整重讀目前版本，不只檢查新增段落。

## 用獨立查核與實際閱讀驗收

每份正式交付的報告都要完成兩種獨立審查：技術查核回到證據確認主張；讀者測試只憑成品回答真實問題。兩種審查使用不同的全新上下文，讀者不能靠研究對話或外部資料替正文補答案。

送審前讀 [references/review.md](references/review.md)，依可用的 agent／工具實際執行。若外層研究流程已安排符合這些要求、且仍適用最終稿的審查，沿用其紀錄即可，不重複建立同樣的審查。

修訂後重審受影響的部分，結果必須對應最終稿。不能只因 reviewer 寫 `ACCEPT` 就交付：核對它實際查了什麼，以及讀者的回答是否符合報告內容。來源或 reviewer 不可用時，可以交付明示未完成審查的草稿，不能自行宣稱通過。

證據足以支持目前有邊界的結論、重要缺口已交代且兩種審查通過後，即可交付。尚未確定本身可以是合格結論。沒有進展的重審按審查指引收斂，不以不斷換句話說或降低標準換取通過。
