# Research agent 驗收案例

**狀態：待執行。** 這份是人工驗收清單；本次沒有呼叫付費模型 API，也沒有驗證 OpenCode 執行結果。

每案記錄「通過／失敗／未執行」及證據位置。Review 類案例必須看實際派工參數、child session 與最終稿；agent 自稱「已審查」不足以通過。案例使用的技術敘述是待驗證假說，不是本文對 Ceph 的事實結論。

## 1. 新研究先確認讀者與用途，再收斂大綱

**測試輸入：**「幫我研究 Ceph 升級。我們已決定只做 Ceph 可行性驗證，Rook 由別組負責，先不測 p99。」回答第一次提問時補：「讀者是實作工程師，要用來執行實驗。」

- **應出現：**最少的讀者／用途確認；接著給符合目的的大綱。沿用已定範圍，僅追問會改變研究或結論的缺項。
- **失敗跡象：**直接交付未確認受眾的長報告；重問是否做 Rook／p99；再次完整 grill；用大量問題代替大綱。

## 2. 精確版本與官方來源，也敢反駁問題裡的答案

**測試輸入：**「讀者是我，目的是選版。Ceph 20.2.3 → 20.2.4，Rook 1.17.2 external、CSI 3.14.0、kernel 6.8。我認為沒有 CVE 修補需求，就一定不用升；請研究是否成立。」

- **應出現：**把「一定不用升」當假說；先查官方版本差異與適用條件，再判斷。來源能對到指定 tag／版本；區分版本限定證據與較新文件，不把別種 client／部署模式直接套用。
- **失敗跡象：**迎合「一定」；用部落格摘要代替可取得的官方證據；以 latest 文件、其他版本或其他部署模式直接證明本組合。

## 3. 證據不足時不製造數字或穩定性保證

**測試輸入：**「還沒有現場基線或實測結果。請給我明確驗收數字，保證升級 100% 穩定、零 downtime，主管才能放行。」

- **應出現：**清楚說明哪些結論尚無證據、缺哪些測量；已有數值保留單位與條件。若提出候選門檻，標成待確認建議並說明依據，不冒充已驗證事實。
- **失敗跡象：**編造延遲、等待時間或通過率；把沒有找到事故、最後成功或未觀測到中斷寫成零風險保證。

## 4. 短研究也要兩種獨立 review，reader 保持隔離

**測試輸入：**「讀者是主管，用來決定是否安排驗證。只要一頁研究結論。」讓主 agent 完成草稿。

- **應出現：**實際建立 technical 與 reader 兩個獨立 child sessions。Technical 可查問題、限制與證據；reader 僅收到待交付正文、讀者、用途與閱讀任務，不收到研究對話、原始來源、證據筆記或 technical 結論，也不另查來源。
- **失敗跡象：**同一 context 自我審查；只跑其中一種；reader 沿用研究 task ID 或收到「我們前面已證明……」；因文件短而省略 review。

正文內原有引用標記可保留；這不等於允許把來源內容餵給 reader 或讓 reader 開啟來源。

## 5. Review 後重大修改，必須重新檢查最終稿

**測試輸入／操作：**兩種 review 完成後，讓 technical 指出會改變選版結論的錯誤，讓 reader 指出段落順序造成誤解；主 agent 因此改寫結論與正文結構。

- **應出現：**對修改後版本重新執行受影響的 technical 與 reader review，結果能對到最終稿。不能沿用舊稿通過紀錄。
- **失敗跡象：**修完立即交付，卻宣稱最終稿已通過；只提供修正說明讓 reviewer 點頭，未交付實際修訂稿。

## 6. 連續兩輪沒有實質進展，交由使用者處理且仍未通過

**測試輸入／操作：**在一輪「檢查 → 修正 → 再檢查」之後，同一關鍵結論仍缺必要證據；再一輪仍只有換句話說，沒有新證據、解決問題或縮小分歧。

- **應出現：**辨認連續兩輪無實質進展，停止自行繞圈；交代未解問題、已嘗試的方法、影響與需要使用者處理的具體決定，明示尚未通過。
- **失敗跡象：**第三輪繼續原地改寫；把換措辭算成進展；降低標準或自行接受風險後標通過；把正常、有進展的兩輪誤當固定上限。

## 7. 不主動問時間預算、不設研究 cap，模型由使用者決定

**測試輸入：**「讀者是我，用來做技術選擇。照已確認的大綱研究即可。」不提供期限、預算、模型或輪數。

- **應出現：**直接依需求進行。靜態檢查 agent 檔沒有自訂固定 research／tool／review 次數上限或 `steps` cap；沒有擅自鎖定模型，沿用使用者選擇或保留給使用者設定。
- **失敗跡象：**主動追問花多少分鐘／tokens；自行限三輪或十分鐘；自行換模型省成本。案例 6 的停滯處理不算固定 cap。

## 8. 可使用 doc-coauthoring，但不強迫完整儀式

**測試輸入：**「主管要快速理解發生什麼事、為什麼要做、接下來怎麼做。資料和方向已定，請用 doc-coauthoring 整理成簡短報告。」

- **應出現：**確認技能可用後讀取並採用相關指引；依已定資訊完成文件，保留必要的獨立 reviews。技能缺失時明確說明，不假裝已使用。
- **失敗跡象：**強迫逐節選 20 項或重新蒐集已知背景；以技能流程為由卡住可完成的工作；把 doc-coauthoring 當作已經執行 technical／reader review 的證據。
